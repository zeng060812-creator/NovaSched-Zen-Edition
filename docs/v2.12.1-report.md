# v2.12.1 修订报告

作者：**ZenJooo** · 2026-10-25

本报告记录 v2.12.1 的根因分析、实现、验证证据与未验证边界。所有"真机"指 Redmi
K70 Pro（houji，23127PN0CC，SM8650/pineapple，HyperOS 4.0.18 / Android 17 SDK 37，
内核 6.1.138，KernelSU root）；测试通过 adb 在该设备上直接运行交叉编译的测试二进制。

## 一、NovaFAS（frame_ctrl.rs）缺陷核实与修复

前期静态审查提出的 8 类问题逐条核实，5 类属实、2 类部分属实、1 类已在 v2.12.0
修复。全部按核实结果处理：

### 1. dump/clear 与累计差分混用（属实，已修复）

旧 `Timestats::sample()` 每次先 `-dump` 再 `-clear`，却用 `total - last_total` 差分。
`-clear` 生效的内核上，下一窗累计从 0 重来，`saturating_sub` 恒为 0 → fps 恒 0、
永远走回落路径。实现"restart 感知差分"（`window_delta`）：当前累计小于上次累计
（clear 生效 / SF 重启 / 图层重建）时取当前累计为窗口帧数，否则差分；首窗与
应用切换后不作差分。两种内核行为下窗口都正确。

### 2. 跨应用信号污染（属实，已修复）

应用切换只重置了 Controller。现在切换时同步作废：窗口计数与主图层归属
（`invalidate_window`）、`frame_ok`、失败计数、`status.fps`，并强制下一拍重写节点。

### 3. 多图层误计 FPS（属实，已修复）

`parse_timestats` 改为逐图层返回（`LayerFrames`），主渲染图层由 `elect_primary`
选举：窗口帧数最多者为候选，已有主图层保持稳定（候选须超过其 2 倍才切换），
图层重建通过去掉 `#序号` 的 base 键跨采样对齐。同应用的菜单/弹窗/Activity 层
不再叠加进游戏 FPS。整窗零出帧时维持主图层身份并返回 fps=0 的合法样本
（"未渲染"），不再误判为信号丢失。

### 4. 目标与实际帧率混淆（部分属实，已修复）

旧逻辑持续不足约 10 秒后无条件重学基线——加压中途（还有空间）也会把低帧率
学成目标，提前放弃。现在基线重学只在两个无歧义边界进行：`boost == 0`（未加压
的实际帧率即真实目标）或 `boost >= ceiling` 仍持续不足（快速收敛接受实际帧率，
让上限加压自然回落——上限加压无收益不得长期挂满）。中间区间继续加压。
应用停止渲染（fps<1）按加倍步长（8/拍）回落。

### 5. GPU 忙持续加压 CPU（属实，已修复）

`on_load` 的加压上限收窄到档位 ceiling 的 60%（`LOAD_CAP_RATIO`）：没有帧时间
证据时，GPU 忙不代表 CPU 需要 uclamp/底频；不再单凭负载推到顶格。中间负载
区间（45–70）不再无限期保留 boost，按低速档节奏回落，与低负载共用迟滞防振荡。
入参不合法（NaN/超界）直接返回当前值。

### 6. 长期无效 boost（部分属实，已补齐）

信号过期泄压（STALE_BOOST_AFTER）v2.12.0 已有；本次补齐"信号有效但无收益"：
上限加压持续不足时快速重学基线并回落（见第 4 条），中段负载不再挂高（见第 5
条），暂停画面加倍回落（见第 4 条）。

### 7. floor 缓存越界 panic（属实，已修复）

`target.clamp(floor_khz, max_now)`：floor 有缓存而 `scaling_max_freq` 会被温控/
外部限频动态压低，缓存 floor 高于最新上限时 `clamp(min > max)` 直接 panic，
引擎线程死亡且加压值悬挂。修复：每拍缓存高于实际上限时作废重解析，使用时
`floor.min(max_now)`，写入用 `.max(floor).min(max_now)`。引擎线程整体包在
`catch_unwind` 中，panic 后按快照释放全部节点并解冻 fas-rs（release 构建为
panic=abort 时由监督进程崩溃恢复路径兜底，代码内已注明）。

### 8. 强制校验被缓存跳过（属实，已修复）

`force_reassert` 只绕过了 boost 去重，每簇 `last_min` 去重仍会跳过真实读回。
现在强制轮绕过 `last_min`，并在写入后读回验证：读回不一致作废去重缓存下一拍
重试，不在缓存里维持从未生效的目标值。

### 9. 采集开销（部分属实，已优化）

- fas-rs 扫描：接管激活时原实现每拍（200ms）全量扫 /proc 读 cmdline，现限频
  到每秒一次（`scan_at`）。
- dumpsys：fps=0 成为合法样本后，暂停/静态画面不再触发"连续失败 → force_retry
  → 反复 fork"路径。

### fas-rs 接管 pidfd 化（真机安全）

SIGSTOP/SIGCONT 一律经 pidfd（434/424 syscall）发送：进程在扫描与停止之间死亡、
PID 被复用时信号落空而不是误停无辜进程；内核 <5.3 无 pidfd 时退回 kill 并在发送
前重验 /proc cmdline 身份（判定标准与扫描一致，`fas::looks_like_fas_pid`）。
`SuspendedFas::Drop` 在任何退出路径（正常/panic/让位）都尝试解冻。

## 二、游戏锁 60/90 排查（只读诊断）

本机（K70 Pro）当前观测到的限制来源（采集时状态，只读，未修改）：

- 温控：CPU7 95°C 温控状态 3（SEVERE），四簇 scaling_max 被压至
  902/1498/1286/1248 MHz（物理 2266/3149/2957/3302）——当时的锁帧主因是热，
  不是调度配置。
- 厂商机制：WALT `sched_fmax_cap`（Scene N1 自带脚本也以它为第一解锁目标）、
  MIUI 热限频 `cpu_limits`/`sconfig`、MIGT/metis、`msm_performance`。
- 刷新率：面板 120/90/60/40/30/24 可选，`peak_refresh_rate=120`；
  `mRefreshRatePackages`（HyperOS 按应用刷新率策略）为空。
- 设备未安装 NovaSched、无 fas-rs、`/data/powercfg.*` 不存在——不存在本模块
  或 fas-rs 造成的锁帧。

新增 `game-diagnose` 的 vendor-limit 只读段输出上述全部证据节点
（walt/thermal_message/migt/metis/msm_performance/game_opt/mi_display/刷新率
settings），用于逐台设备回答"限制来自哪里"。模块不修改这些节点，不通过关温控
掩盖问题。结论：无法在不运行具体游戏的情况下断言某游戏锁帧的单一原因；
诊断路径已就位，需要出现掉帧/锁帧时采集 `game-diagnose` 输出对应分析。

## 三、天玑 9500（MT6993）适配

- 识别：`mtk_platform("mt6993")`、营销名 Dimensity 9500 / 天玑9500；近误型号
  （9400/9400 Ultra/95000）不误认。
- 拓扑准入：[0,4,7]（4×A725 + 3×A725 + 1×C1-Ultra），与采集报告的 policy0/4/7、
  逐核 MIDR、capacity 逐项一致（夹具 `dimensity9500-cpuinfo.txt`）。
- 模板：`generate-profiles.py` 生成（字节级校验），governor 显式 `sugov_ext`
  （真机 OEM 默认），频点包络按 OPP 表推导（p0 2700 / p4 3500 / p7 4210）：
  省电 52/46/45%、均衡 60/54/52%、性能 82/80/80%、极速 95/100/100%。
  **候选值——识别与准入已验证，能效未验证**。
- GPU：MaliG1Ultra（gpufreqv2 私有接口，无标准 devfreq 节点；采集确认本机
  devfreq 仅 UFS）。`gpu_devfreq` 不携带，功能停用并告警降级，不影响 CPU 调度。

## 四、Scene 兼容（N1 核实）

- 已安装版本实测：`com.omarea.vtools` versionName **"N1 2026.10 Beta6"**
  （versionCode 920261021，targetSdk 36，安装于 2026-10-19）。用户所称 "N1" 即
  该版本线。
- 协议核实来源：从该设备 Scene 私有目录取回其自带 `files/powercfg.sh`——与
  模块的 provider 协议一致：Scene 以 `/data/powercfg.sh <mode>` 调用四档
  （powersave/balance/performance/fast + standby/init，pedestal 已废弃返回 0），
  `/data/powercfg.json` 供展示，`mode.txt` 供状态回读。`scene.rs` 的
  `powercfg.xml` 应用规则同步与 `package-restrictions` 校验维持不变。
- 控制权：检测到 Scene 配置了外部调度器时 `controls_locked`，NovaSched 让位且
  退出不覆盖对方节点；NovaSched 作为 provider 时四档由本模块执行。SIGSTOP
  接管 fas-rs 的 PID 复用风险已在本次 pidfd 化中消除。
- 本设备 Scene 未配置调度提供者（powercfg.sh 未落盘），注册链路在装机后
  首次启动时验证。

## 六、按应用图形后端规则（ANGLE）

- 机制：Android `GraphicsEnvironment` 在应用进程启动时读取
  `angle_gl_driver_selection_pkgs` / `angle_gl_driver_selection_values`
  （逗号列表按下标对应，值 angle/native）。模块规则存
  `/data/adb/novasched/config/graphics_rules.json`，写入共享设置并读回确认。
- 边界（按用户要求如实声明）：
  - 仅提供经过系统入口验证的 ANGLE / native 后端；**不提供"强制任意游戏
    Vulkan"**——Android 无公开按应用 Vulkan 入口，模块不做做不到的承诺；
  - 本机实测 `com.google.android.angle` 不存在 → `graphics-status` 如实报告
    `angle_driver_available=no`，`graphics-set` 保存规则但拒绝写系统设置
    （真机验证通过），不伪造支持；
  - 生效需目标应用完全退出重开；不强杀进程；恢复只撤销本模块写入且未被
    外部修改的表项（所有权记录 `restore/graphics-owned.json`）。
- CLI：`graphics-status / graphics-sync / graphics-set PKG angle|native /
  graphics-remove PKG / graphics-revert`；`diagnose` 输出状态段；卸载流程
  自动 `revert_owned`。

## 七、WebUI 流体交互与信息

- 物理弹簧：morph（弹窗/面板）与页面切换改为欠阻尼二阶系统（ζ≈0.84）按
  16ms 采样的 WAAPI 关键帧，每帧 `easing:"linear"`，时长由收敛阈值推导
  （约 430ms）——不是把 cubic-bezier 宣称成弹簧。
- 中断续接：动画/拖拽进行中重新触发时，从 `getComputedStyle` 矩阵继续
  （特性检测缺失环境退回端点起播）；面板下拉释放按位移与速度（px/ms，
  120ms 窗口）判定完成/取消，甩动关闭的动画从拖拽位置连续过渡。
- 信息：无信号帧率显示"待渲染"而不是 0.0 fps。reduced-motion、代次控制、
  焦点管理维持 v2.12.0 结构。
- 验证：`test-webui-dom.cjs` 29 项全过（含快速连点切页、关闭途中重开、叠层
  弹窗、手势取消、motion 回退）；`test-glass-ui.cjs` 29 项全过（源码断言同步
